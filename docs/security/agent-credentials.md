# Agent credential foundation

Agents use per-agent opaque bearer credentials independently of human Keycloak/OIDC identity. Each credential contains 256 bits from JDK SecureRandom and has a strict `pm_agent_` URL-safe form. PostgreSQL stores only SHA-256 of the high-entropy credential, never plaintext. This is not password hashing; credentials must be generated, not chosen by users.

The application service rotates a credential only for an active agent in an active, exact organization. Rotation locks the scoped agent and organization rows, revokes the previous credential and stores the new digest in one transaction. A partial unique index also limits each scoped agent to one unrevoked credential. The tenant binding is a composite database foreign key. Revoked rows are retained. Validity must be explicit, positive and at most 90 days; there is no perpetual credential.

Authentication derives the organization and agent from the digest's database row and checks expiry, revocation and current agent/organization status. Client-supplied tenant or agent identifiers are not identity evidence. Database errors propagate so a transport adapter must reject authentication on infrastructure failure. Never log the bearer credential; the issuance value's string representation is redacted.

Human PLATFORM_ADMIN users may rotate credentials through POST /api/v1/agents/{agentId}/credentials/rotate with an explicit validitySeconds (1 through 7776000). The tenant comes from the verified OIDC subject and active database membership, never headers or request bodies. Cross-tenant or inactive targets return a generic 404. The 201 response exposes id, secret and expiresAt once with Cache-Control: no-store. The dedicated /api/v1/runtime/** security chain accepts exactly one opaque Bearer credential and derives organization/agent from PostgreSQL. It discards inherited human/session identity, grants only runtime:submit, and accepts POST only. Ordinary human APIs continue to require OIDC JWTs, so agents cannot rotate credentials or approve actions. Runtime submission remains pending; it must not accept risk, timing or grant eligibility assertions from the caller. Plaintext may be returned exactly once to an authorized issuer, with no-store response caching and redacted application logs. Use loopback-only HTTP for local development and authenticated TLS on any non-loopback network.


Runtime admission is a shared PostgreSQL fixed-minute limit per organization/agent (default 60, configured by proofmesh.agent.requests-per-minute, range 1–10000). Database time defines the window, and rotation does not reset the agent quota. Concurrent requests arbitrate on the same row; an exceeded limit returns 429 with Retry-After: 60. Fixed windows may admit up to twice the configured quota across a minute boundary. Credential or admission database errors return 503 without invoking a handler. Non-runtime routes reject agent credentials.

An append-only agent_runtime_audit row records ADMITTED or RATE_LIMITED with tenant, agent, id and database timestamp. Audit persistence is mandatory in the admission transaction. These events prove transport admission, not policy ALLOW or tool execution. Unidentified malformed/unknown credential requests are rejected without storing a claimed identity or secret; this table is not a comprehensive authentication-failure log. No headers, tokens, payloads or response content are stored here. Database owners can bypass triggers; local demo credentials must not be treated as hardened database-role deployment. No retention deletes are performed.
